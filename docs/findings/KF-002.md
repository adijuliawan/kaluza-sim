# KF-002: the AMF's UE Security Capabilities are one bit off, hiding NIA1 and offering NEA3/NIA3

- Found: 2026-10-17 09:04 KST (LW5a), kaluza-sim release ab9e23a1bb32, kaluza-core's lab AMF localhost/kaluza-amf:671c7c89 (kaluza-core 1d0b91cd checked out read-only for the cause). Scenario `gates/verification/ksim-p2-security.sh` on `topologies/split-lab-nea1.yaml` (our CU-CP preferring NEA 1, 2 and NIA 1, 2), UE 1, imsi-001010000300000, seed 42.
- Row: ksim-p2.as-nea1-nia1, which wants the AS SECURITY MODE COMMAND to select NIA1/NEA1. It got nia2/nea1.
- Clause: TS 38.413 V19.4.0 §9.3.1.86, NR Encryption Algorithms: "'all bits equal to 0' – UE supports no other algorithm than NEA0, 'first bit' – 128-NEA1, 'second bit' – 128-NEA2, 'third bit' – 128-NEA3". The same holds for NR integrity (NIA), E-UTRA encryption (EEA) and E-UTRA integrity (EIA). TS 24.501 §9.11.3.54 puts 5G-EA0 in bit 8 of octet 3 and 128-5G-EA1 in bit 7; the NGAP bitmap has no bit for algorithm 0.
- Expected (per spec): for the UE's 5G-EA0/EA1/EA2 (octet e0) and 5G-IA1/IA2 (octet 60), nRencryptionAlgorithms c000 (NEA1, NEA2) and nRintegrityProtectionAlgorithms c000 (NIA1, NIA2).
- Observed: e000 (NEA1, NEA2, NEA3) and 6000 (NIA2, NIA3). NIA1 reads as not supported, and NEA3/NIA3, which the UE lacks, as supported. Our CU-CP, preferring NIA1, had to choose NIA2. A gNB preferring NEA3 or NIA3 would select an algorithm the UE does not have.
- Cause (read in kaluza-core, never edited): `proto/kaluza-ngap/src/main/java/io/kaluza/proto/ngap/ies/UeSecurityCapabilities.java`, `fromNas()`, builds each field as `(nas[i] & 0xFF) << 8`. That copies the NAS octet with its algorithm-0 bit into the first bit. Its javadoc says §9.3.1.86 puts "algorithm 0 in the most significant bit of the first octet", which the clause above contradicts.
- Evidence: `runs/lab/kaluza-20261017T000452Z`:
  - `cucp/ngap.pcapng` frame 3, InitialUEMessage, Registration request: UE security capability 5G-EA0/1/2, 5G-IA1/2;
  - frame 8, InitialContextSetupRequest: UESecurityCapabilities nRencryptionAlgorithms e000, nRintegrityProtectionAlgorithms 6000;
  - `events.ndjson` seq 35-36: rrc.smc.complete and ran.as.smc, alg nia2/nea1.
- Cross-check: the Open5GS fork core gave the same UE persona c000/c000 in both NEA1/NIA1 rig runs (runs open5gs-20261016T142025Z frame 10, open5gs-20261016T142029Z frame 8, 2026-10-16 23:20 KST), and the row passed there with nia1/nea1.
- Sim mutant that would hide it: none. Our CU-CP intersects its preference list with what the AMF says the UE supports, as TS 33.501 V19.7.0 §6.7.3.0 has the gNB do ("the highest priority from its configured list and is also present in the UE 5G security capabilities").
- Handed to: kaluza-core-92, 2026-10-17 09:06 KST; confirmed by it the same morning. Their register row: **AMF F-80** (🟠). Fixed on a local branch: `fromNas()` now does `(octet & 0x7F) << 9` for all four families, so this UE's e0/60 goes out as c000/c000. Their wave-19 test had read Open5GS's e000 for a rig UE's f0f0f0f0 as Open5GS narrowing out ZUC, when it was the correct shift. That test now asserts their octets match Open5GS's. The fix is not on the lab; when it rolls is the user's call (kaluza-core-92 suggests the apply after P2 Q16).
- Until the AMF rolls, row ksim-p2.as-nea1-nia1 on kaluza-core is known (F-80). Its re-run belongs in the next window after the roll.
- **Status:** open (fixed on kaluza-core's branch, not on the lab).
