# KF-001: a PDU session request for a DNN no SMF serves gets no answer

- Found: 2026-10-15 17:46 KST (W2), kaluza-sim release 0b1241874b7f, kaluza-core images live then (from kaluza-core-df):
  - AMF localhost/kaluza-amf:d83d40a6 (JVM);
  - SCP 963130e1-native;
  - SMF 68fe6998-native;
  - UDM/NRF/NSSF/SMSF/SMSC 963130e1-native.
  Scenario `gates/verification/ksim-p1-session.sh` on `topologies/aio-lab.yaml` (UE 3, imsi-001010000300002), seed 42.
- Row: ksim-p1.backoff. On a real core the gate sends one PDU SESSION ESTABLISHMENT REQUEST for DNN `ksim-backoff`, which no subscriber of the block has. The row stays unscored on kaluza-core while this finding is open.
- Clause: TS 24.501 j80 §5.4.5.2.5, item 1 v: "if the SMF selection fails, then the AMF shall send back to the UE the 5GSM message which was not forwarded as specified in clause 5.4.5.3.1 case e) or case f)", that is, a DL NAS TRANSPORT with 5GMM cause #90 "payload was not forwarded".
- Expected (per spec): that DL NAS TRANSPORT, soon after the request and well inside T3580 (16 s).
- Observed: nothing for that UE on N2 for 16 s. The UE's T3580 expired and it retransmitted (§6.4.1.6). The gate then switched the UE off, 18 s after the request. kaluza-core-df traced it in the core's logs (UTC):
  - 08:46:57.998 AMF: the request for PSI 1 arrived while the internet session's release was still finishing, so the AMF released the old context as a duplicate. At 08:46:59.017 it started establishing PSI 1 anew with DNN ksim-backoff.
  - 08:46:59.026 SCP (Model D delegated discovery): no SMF profile serves dnn=ksim-backoff; at 08:46:59.035 it originated 400 NF_DISCOVERY_FAILURE.
  - 08:46:59.040 AMF: "the SMF refused with 400", and nothing went to the UE. In SmPayloadHandler, a refusal that carries no N1 (an unavailable SMF, say) falls through to an empty answer. The SMF never saw the request, so §6.4.1.4.1's #27 reject could not arise; this is §5.4.5.2.5's case.
- Evidence: `runs/lab/kaluza-20261015T084553Z` (kaluza-sim's run directory):
  - `ngap.pcapng`: the UplinkNASTransport at 2026-10-15T08:46:57.973Z (RAN UE NGAP ID 4, AMF UE NGAP ID 21), and no DownlinkNASTransport for that UE until the retransmission at +16.0 s;
  - `events.ndjson`: seq 437 nas.sm.est.request (dnn ksim-backoff, PSI 1, PTI 5) and seq 446 nas.sm.timer.expiry T3580;
  - ens19 capture: `~/.kaluza-sim/lab/ksim-w2-ens19.pcap` on the dev PC (0600; raw NGAP holds keys, so it stays out of the repo).
- Cross-check: the Open5GS fork core (741c29d8d, rig run open5gs-20261015T094554Z, 18:46-18:54 KST) is silent too, both for the same request (`ksim-backoff`: nothing for 30 s) and for an `ims` request from subscribers we provisioned without that DNN. The fork agrees with kaluza-core here, against the clause; per the findings rules the finding stands and the agreement is recorded. Our stub answers #29 with a back-off timer for this DNN, by design.
- Sim mutant that would hide it: none.
- Handed to: kaluza-core-df, 2026-10-15; confirmed by it as a core defect the same day. Their register row: **AMF F-76**. Fixed on their branch p76-p77-idp-retry-n3ue-capture (f51ccdb1), not yet on the lab:
  - a failed SMF selection (Model D's SCP 400 NF_DISCOVERY_FAILURE, Model C's empty selection) sends the 5GSM message back with its PSI and 5GMM #91 when the DNN is not subscribed on the S-NSSAI, #90 otherwise;
  - an unavailable SMF gets #90.

  Until the AMF image rolls, row ksim-p1.backoff on kaluza-core is known (F-76). After it rolls, expect #91 for `ksim-backoff`.
